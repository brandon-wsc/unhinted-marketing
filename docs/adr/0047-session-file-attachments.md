# ADR 0047 — Session file attachments (chat import + document retrieve)

- **Status:** Proposed (§10 scan-failure path amended by [0048](./0048-scanned-pdf-ocr-transcript.md))
- **Date:** 2026-10-18
- **Supersedes:** [ADR 0019](./0019-pydantic-ai-inner-harness.md) §4 in part — keeps "documents are `attachment_id` tools returning slices", replaces the external HTTP document service with in-process worker ingest (parser + chunker ship in the worker, never in the request path or the LLM loop). Extends [COLLECT](../knowledge/COLLECT.md) §3 inventory.

## Context

COLLECT today is **row-shaped only**: product catalog via CSV/XLSX where one row = one retrieve unit. There is no path for document-shaped knowledge (PDF product sheets, DOCX briefs, price-list docs, pasted specs) — neither in settings import nor in chat. Users need to attach files mid-session ("公司 product PDF") and have the turn ground against them.

[ADR 0019](./0019-pydantic-ai-inner-harness.md) already locked the shape: documents are `attachment_id` tools returning slices; full text lives in the PG ingest plane, never in prompts. Its §4 also assumed an external document service; this ADR drops that — the on-prem floor cannot afford another long-lived process, and the ADR 0039 job queue + worker already gives an out-of-request execution home.

Two constraints drive the design:

- **Embedding window + dilution.** The shipped embedder (`paraphrase-multilingual-MiniLM-L12-v2`, 384-dim) was trained at 128 tokens; FastEmbed truncates at 512, so text past 128 is not cut but degrades quality, and ADR 0040's retrieve eval quantified mean-pooling dilution (~130-token needle in a 512-token doc ≈ +0.06 cosine; past 512 contributes zero). One-doc-one-vector is useless; chunks must stay inside the 128-token trained window — measured in **tokens**, not chars (XLM-R tokenizer ≈ 1+ token per CJK char) — and carry their own context.
- **On-prem CPU floor.** Local benchmark: ~30–40 chunks/s on arm64; low-end Celeron estimated ~4–12 chunks/s (no AVX2 on Atom-derived parts), ~500 MB RSS per embedder process. A 150–200-chunk doc takes ~20–50 s there — so no user-visible action may wait on embeddings.

## Decision

1. **Two new tables, separate from `products`.**
   - `attachments` — file row: `company_id`, `owner_scope` (`session|user|org`), `user_id`, `session_id` (scratch), `filename`, `content_type`, `object_key`, `status` (`pending|ready_lexical|ready|failed`), `doc_profile` JSONB, `error`.
   - `document_chunks` — `attachment_id`, `chunk_index`, `text`, `heading_path`, `page_start/end`, `embedding vector` (dimensionless), `embedding_model`.
   - Doc chunks are **never** pseudo-rows in `products` — `(company_id, sku)` uniqueness and `pick_primary` margin semantics must not see them.
   - Same PostgreSQL ingest plane, not a parallel knowledge store: signals/entities/edges model *market* knowledge with source URLs and decay; doc chunks are tenant-owned file slices with owner scope and file lifecycle. Folding them into `signals` would leak scratch files into ranking and break GC.
2. **Scope follows the existing 2×2 ownership matrix.** Chat upload lands as **User × New session scratch** — session-scoped, retrievable across the session's turns, dies with the session, never written to committed tables. **「存入我嘅庫」is an explicit HTTP action** → User × Old (Mine). Org library and Mine→Org promotion for docs reuse the K6 proposal/Approvals shape later (knowledge commit stays HTTP, never a chat phrase — [ADR 0011](./0011-knowledge-commit-without-llm.md)).
3. **Chat import shape.** `POST /api/sessions/{id}/attachments` stores bytes in the media object store under a new `attachments/` key prefix (the `sessions/{id}/r{rev}` image pattern stays image-only); `PostMessageRequest` gains `attachment_ids[]` — each id is validated to belong to this session's scratch or the member's user/org library (cross-tenant ids → 404). Attach once, reference in one or many messages. Attachment bytes are **never** served by the unauthenticated `GET /api/media/{key}` route — today it streams *any* path-safe key under `MEDIA_ROOT`, so the same change restricts it to the `sessions/` image prefix. Original-file download is a separate authenticated `GET /api/attachments/{id}/download` behind `require_company_access`.
4. **Chunking = structure-aware + recursive split + overlap** — not embedding-drift "semantic chunking".
   - **Parsers:** PDF via `pypdfium2` (Apache-2.0 / BSD-3 — text per page + outline via `get_toc()`); DOCX via `python-docx` (heading styles); MD/TXT native. PyMuPDF is rejected: AGPL-3.0 conflicts with this repo's MIT license and on-prem distribution (ADR 0026/0027).
   - **Structure first:** PDF outline / DOCX heading styles / MD headings bound chunks; a chunk never spans two headings.
   - **Recursive split within a unit:** `段落 → 行 → 句 → 字`. Sentence separators cover full- and half-width `。！？；!?;`, Latin `. ` / `? `, line breaks, and emoji runs (HK copy often breaks on emoji/space).
   - **Length is token-counted** with the embedder's own tokenizer (char count only as fallback): target ~100–110 tokens **including** the heading prefix, so the embed input stays inside the 128-token trained window.
   - **Overlap is sentence-aligned:** carry the previous sentence (~10–15%), never a char slice; overlap never crosses a heading or table boundary.
   - **Heading path is metadata, not stored text.** `text` holds the raw chunk; `heading_path` is its own column. Embed input = `[產品目錄 > 優惠詳情] ` + `text` (cheap contextual retrieval); refs render from `heading_path` + page ("p.3 · 優惠詳情"). Lexical `strpos` runs on raw `text` only, so heading words do not hit every chunk in a section.
   - **Tables** stay atomic ≤ cap, no overlap; oversized tables split by row group with the header row repeated.
   - **Caps:** ~150 chunks/doc, ~10–20 MB/file.
5. **LLM sees digests, never full text.** Ingest emits a deterministic `doc_profile` — `title`, `pages`, `outline[]`, `kind_guess` (SKU-density / price-token / table-ratio heuristics, no LLM), ~200-char `preview`. `SessionState` gains `attachments[]` holding digests only (~150–250 tokens/doc); the chat payload budget table gains a row. The chat system prompt forbids pretending to have read an attachment.
6. **`read_attachment` is the only door.** A read-only Pydantic AI tool (in-loop tools stay read-only per ADR 0019): `read_attachment(attachment_id, query? | section?)` → ≤5 slices `{chunk_id, ref, text}` + `partial` flag; ≤2–3 calls per turn. `query` runs the same hybrid lexical + pgvector + RRF retrieve over that doc's chunks; `section` slices by heading path and works before any vector exists. Slice shape copies `signal_slices()` — ids + short fields, never full pages.
7. **Ingest is async and progressively usable** via the ADR 0039 Postgres job queue — never in the request thread. Extract → `doc_profile` → chunks land in ~1–3 s → status `ready_lexical` (digest, `strpos`, section slices already serve); embeddings flush batch-by-batch → `ready`. `partial: true` on tool responses while vectors fill. The **worker** warms the embedder at job claim / worker lifespan — never the API process at upload time, since the embedder copy that matters lives in the worker — and caps ONNX intra-op threads (1–2) so a running ingest does not stall live turns on a 2–4-core box. Warmup is **blocking** in the worker: today's `_get_model()` returns `None` while loading, so a non-blocking path would write `NULL` vectors and still flip `ready`. Rule: an attachment reaches `ready` only when every chunk has a vector for the active `embedding_model`; chunks left `NULL` keep it at `ready_lexical` and re-enqueue an embed job.
8. **Ambiguity asks, doesn't pretend.** A zero-instruction upload is ambiguous by construction: chat replies with the digest + action chips (`用呢份嘢出 post` / `存入我嘅庫` / `講吓重點`) — same spirit as `ask_clarify` and the recommended-questions chip UX. The save chip is a UI action → HTTP endpoint, not a chat phrase.
9. **Embeddings stay local for now** (MiniLM 384; no API provider in v1). `embedding_model` + dimensionless `vector` keeps a second space possible later (cloud API provider, or `bge-m3` on-prem) without re-migration; two spaces never share one index — every retrieve filters its active `embedding_model`. **No ANN index in v1:** pgvector HNSW/IVFFlat needs fixed dimensions, and `read_attachment` always scopes to one attachment (≤150 chunks), so exact scan is enough. When cross-document library search lands, add a partial expression index `((embedding::vector(384))) WHERE embedding_model = …` per space. A second space also needs `EMBEDDING_DIM`'s hard 384 check in `internal/memory/embeddings.py` made per-model.
10. **Failures tell the truth — and don't retry.** Image-only/scanned PDF → "讀唔到字" (OCR deferred); encrypted/corrupt → clear error; over-cap → ingest first N chunks and say so (`partial` on profile). Parse failures are **permanent**: the attachment row goes `status=failed` + `error` and the job itself succeeds — a corrupt file never burns job retries. Same "skip + report" posture as product import errors.
11. **Grounding:** tool-returned `chunk_ids` join the grounding-id family next to `source_signal_ids` / `product_context_ids`; `grounding_check` treats doc claims like product claims (must match a retrieved slice, no invented specs).
12. **CSV/XLSX stay product-path only** — the attachments endpoint refuses them with a pointer to the product import path rather than silently ingesting them as documents; the two ingest paths stay cleanly separated.
13. **Fork shares attachments by reference.** An `attachment_sessions` join records which sessions reference an attachment; fork ([ADR 0017](./0017-session-fork.md)) inserts the new session for every attachment reachable from the copied messages, so digests keep hydrating in the fork. Chunks + object bytes exist once — GC deletes them only when the **last** referencing session is deleted (same share-by-ref posture as preview media keys, ADR 0017/0024). Digests hydrate per turn from the join, never from `session_id` alone — a fork must not silently lose its files.
14. **Scope is enforced server-side, not trusted.** `attachment_ids` on POST /messages are validated against session/member scope (decision 3); `read_attachment` re-checks `company_id` + owner scope on every call — the tool never trusts an id the LLM produced. Scratch attachments are capped per session (~10) to bound digest tokens.

## Consequences

- New surface area: `POST/GET …/sessions/{id}/attachments`, authenticated `GET /api/attachments/{id}/download`, a save-to-library endpoint (Mine), `attachments[]` on SessionState + `MessageResponse` (UI chips), `read_attachment` tool, `attachment_chunk_ids` grounding field, `attachment_sessions` join, `attachment` object-key prefix + sniff/parse for pdf/docx/txt/md. New runtime deps: `pypdfium2` (bundles PDFium wheels for arm64/x86_64 — no system lib) and `python-docx`; no AGPL dependency.
- The same change tightens `GET /api/media/{key}` to the `sessions/` prefix — it currently streams any path-safe key under `MEDIA_ROOT` unauthenticated.
- Scratch lifecycle: chunk rows + object bytes are GC'd when the **last** referencing session is deleted (join-table ref count — simpler than the media ref-peeling path); an optional janitor sweep for scratch attachments whose sessions were never deleted can ride the job queue later.
- Worker process loads its own embedder copy (~500 MB RSS) when claiming ingest jobs — acceptable on the on-prem floor only if threads are capped; a future sidecar embed service is the mainstream alternative if RAM binds.
- Deferred (explicit non-goals for v1): doc→product extraction (mint `products` rows from a catalog PDF), OCR, org Approvals flow for docs, settings Documents tab, HyDE / multi-query for doc retrieve, reranker, second embedding space.
- Eval: extend `scripts/eval_retrieve.py` with doc-chunk cases — needle-in-doc, zh-HK paraphrase, SKU-exact, `kind_guess` fixtures — same keyless style.
